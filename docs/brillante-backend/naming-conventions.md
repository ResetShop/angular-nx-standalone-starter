# Naming conventions

These rules apply to every new table, column, type, constant, endpoint and document of the Brillante backend. They are
decided, not suggestions: a deviation is first recorded as a dated decision in the document it affects. Legacy names appear only in the bridge
schemas (the Drizzle schemas that read the legacy MySQL database during Stage 1) and in
[`legacy-dictionary.md`](legacy-dictionary.md). Stage 1 is the new backend running over the legacy MySQL database; Stage 2
is the move of the data to Postgres.

Some points are marked **open**: they are decided in the review of the context that needs them, or in the architecture
decision named next to them.

## 1. Language

All names, code, comments, documents, tests, test data, API paths and fields, log messages and error messages are in
**English**. Spanish exists only in user-facing text:

- the frontend translation files;
- the backend email templates (user-facing text generated by the backend, kept in dedicated template files);
- data that staff type themselves (see [Translations](#11-translations)).

Known follow-up: the seeded identity role names are Spanish (`Brillante`, `Encargado Local`, …). They become English and
are translated in the frontend by role code.

## 2. Tables

- `snake_case`, **singular**, no technical or legacy prefix: `repair`, `customer`, `repair_status_history`.
- Join tables are named after both sides in business order: `user_role`.
- Lookup tables (closed catalogues) follow the same naming: `repair_status`, `device_type`.
- Avoid SQL reserved words as names (`user`, `order`, `group`, `transaction`). Identity already has a `user` table, which is
  always quoted; new tables do not add to that.

## 3. Keys

| Kind                        | Rule                                              | Example                           |
| --------------------------- | ------------------------------------------------- | --------------------------------- |
| Primary key                 | `id`, the same as the identity module             | `repair.id`                       |
| Foreign key                 | `<referenced_table>_id`                           | `repair.customer_id`              |
| Self reference              | `parent_<table>_id`                               | `<table>.parent_<table>_id`       |
| Same table referenced twice | `<role>_<referenced_table>_id`                    | `<table>.source_office_branch_id` |
| Audit references            | `created_by`, `updated_by`, referencing `user.id` | `repair.created_by`               |

An id column always says which table it points to, except the audit pair `created_by` / `updated_by`, which always point
at `user.id`. The identity tables need no exception for their keys: `repair.customer_id → customer.id` and
`repair.created_by → user.id`. Examples use illustrative names; real entity names are decided in the context reviews.

## 4. Columns and TypeScript properties

- Database columns are `snake_case`; TypeScript properties are `camelCase` with the same words
  (`customer_id` ↔ `customerId`).
- The TypeScript property is the ubiquitous name. In the Stage 1 bridge schemas the property already carries the new
  name while the MySQL column keeps its legacy name: `deviceManufacturer: varchar('marca', { length: 256 })`. The manufacturer stays free text until a later follow-up replaces it
  with a staff-managed reference table.
- A value object stored as columns of its owner prefixes its columns with the value object's name:
  a device becomes `device_type_id`, `device_manufacturer`, `device_model`, `device_identifier`.
- No abbreviations, except the terms listed in the [glossary](glossary.md).

## 5. Lifecycle status

An entity's lifecycle is a **`status`** column of the shared Postgres enum type `record_status`
(`active`, `disabled`, `deleted`), never a pair of booleans. The identity module's `user_status` stays as it is.

- `active`: in use.
- `disabled`: kept and visible to administrators, not selectable for new work.
- `deleted`: logically removed; the row stays (history and audit keep referring to it).

The legacy pair `enabled` / `deleted` maps with this precedence: `deleted` wins, then not enabled → `disabled`,
otherwise `active`.

`status` (lifecycle of a record) is not the same word as a workflow state such as the repair status. The glossary has two
entries, **record status** and **repair status**, and the column of a workflow state is always `<name>_status_id`.

Adding a value to the enum is a migration (`ALTER TYPE … ADD VALUE`). On Postgres 12 and later it may run inside a
transaction, but the new value cannot be used until that transaction commits, so a migration that adds a value and a
migration that uses it are separate steps. Values are **never removed or reordered** in practice; see the next section.

**Deletion audit:** business tables have no `status_changed_*` or `deleted_at` columns. Who disabled or deleted a record,
and when, is `updated_by` and `updated_at`: they record the last change, which includes the status transition. Re-enabling
or reactivating a record overwrites them with the new change. (The identity module keeps its own `status_changed_*` and `deleted_at` columns.)

## 6. Deprecating a status

The three lifecycle values are structural, so retiring one is not expected. If it ever happens, the domain stops using it,
a data migration re-labels the rows that carry it, and the value stays in the enum type: enum values are never removed
or reordered.

Business catalogues are not enums. Their values are retired by setting their own `status` to `disabled`
(see [`lookup-tables.md`](lookup-tables.md)).

## 7. Flags

A genuine yes/no fact that is not lifecycle is a boolean named `is_…`, `has_…`, `was_…` or `allows_…`:
`allows_installments`, `was_powered_on_at_intake`. A boolean is never used to represent "enabled" or "deleted".

## 8. Audit and time

| Kind of table                        | Columns                                                                                                                                    |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| State tables (entities, aggregates)  | `created_at`, `updated_at`, `created_by`, `updated_by`                                                                                     |
| Append-only tables (history, ledger) | `created_at`, `created_by`; no `updated_*`. A history interval ends with its own `closed_at`, the one permitted later write to such a row. |
| Join tables                          | `created_at`                                                                                                                               |
| Lookup tables seeded by migration    | `created_at`, `updated_at`                                                                                                                 |

- Timestamps are `timestamptz`, `not null`. A `timestamptz` stores an absolute instant; connections use `TimeZone = UTC`,
  and Drizzle columns are declared with `{ withTimezone: true, mode: 'date' }`.
- The legacy MySQL `datetime` and `timestamp` columns carry no zone. Until the live database has been checked against known
  rows, they are **assumed to hold UTC**, and the Stage 1 repositories convert them to instants in one place. The check is
  part of the MySQL access work.
- Business instants end in **`_at`** (`finished_at`, `received_at`); calendar dates end in **`_date`** (`birth_date`).
  Business time is never stored in the audit columns.
- The acting user in `created_by` / `updated_by` always comes from the session, never from a request body.
- The business day (cash day, "repairs received today") is a value object computed in `America/Argentina/Buenos_Aires`.
  **Open:** whether cash movements also store the computed `business_date` is decided in the cash review.
- **Open (concurrency):** whether aggregate roots carry a `version` column for optimistic concurrency is decided in the
  architecture decision on repositories and units of work.
- **Open (system actor):** the data move has no acting user; whether migrated rows get a system user or a null
  `created_by` is decided in the data-quality work.

## 9. Money

Amounts are named `<name>_amount` and stored as **integer minor units** in `bigint` (an `integer` overflows at about
21 million pesos), following Fowler's Money pattern. **Open:** how the currency is stored (a currency column per row or per
amount) is decided in the Money architecture decision. In the Stage 1 bridge schemas the legacy `decimal` columns are
converted to Money at the repository boundary.

## 10. Uniqueness and soft delete

Unique keys are **global**: a deleted or disabled record keeps its key, and a record that comes back with the same key
reactivates the existing record (for example a customer with the same national id number), which keeps its history
together. A context document may state that a key must hold only among live records; that key is then a partial unique
index `WHERE status <> 'deleted'`, named `<table>_<columns>_live_key`.

## 11. Translations

- **System-defined, closed lists** (repair status, movement type, device type, payment method): the lookup row has a
  stable English `code` and an English `name`; the frontend shows the Spanish label chosen by `code`. The API returns
  `code` and `name`, never Spanish text.
- **The `record_status` values** are an enum, not a lookup: the frontend translates them by value, and the API returns the
  value.
- **Data that staff create and edit** (movement concepts, office branches): stored exactly as typed and never translated.
  Giving such entries a code by slugifying their names is possible later and is out of scope for now.

## 12. Lookup data

Closed catalogues live in lookup tables, not in database enums or numeric ids in code: see
[`lookup-tables.md`](lookup-tables.md). Domain code refers to a row by its `code`.

## 13. Constraints and indexes

| Kind                    | Pattern                      | Example                           |
| ----------------------- | ---------------------------- | --------------------------------- |
| Primary key             | `<table>_pkey`               | `repair_pkey`                     |
| Unique                  | `<table>_<columns>_key`      | `customer_email_address_key`      |
| Live unique (exception) | `<table>_<columns>_live_key` | `customer_email_address_live_key` |
| Foreign key             | `<table>_<column>_fkey`      | `repair_customer_id_fkey`         |
| Index                   | `<table>_<columns>_idx`      | `repair_customer_id_idx`          |
| Check                   | `<table>_<rule>_check`       | `repair_price_amount_check`       |

Postgres truncates identifiers longer than 63 bytes silently, which can make two names collide. So every constraint and
index is **named explicitly** in the Drizzle schema (Drizzle's default names differ from these patterns), a name is
at most 63 characters, and one that would be longer abbreviates its column list with a glossary-approved short form. A
check script that fails above 63 characters is planned with the first Postgres schema. The identity tables keep their
existing names.

## 14. API and code names

- Resource paths: plural, `kebab-case` (`/repairs`, `/office-branches`); domain operations are sub-resources with a verb
  or event noun (`POST /repairs/{id}/status-changes`). The complete API conventions are an architecture decision.
- Types and classes `PascalCase`, files `kebab-case`, constants `SCREAMING_SNAKE_CASE`, per `CLAUDE.md`.
- Domain events are named in the past tense (`RepairStatusChanged`).

## 15. Differences from the identity module

The identity module (users, roles, permissions) is already live and is not renamed. It follows the same key rules (`id`,
`<table>_id`). It differs in these ways, which are not copied by new tables:

| Identity today                                                             | New tables                                                                            |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `timestamp` columns, nullable, default now                                 | `timestamptz not null`                                                                |
| No `created_by` / `updated_by`; `status_changed_*`, `deleted_at` on `user` | Audit columns of section 8; deletion audit is `updated_by` / `updated_at` (section 5) |
| History tables use `changed_at` / `changed_by`                             | Append-only tables use `created_at` / `created_by`                                    |
| Drizzle default constraint names (`idx_role_code`)                         | Explicit names of section 13                                                          |
| `user_status` enum                                                         | `record_status` enum                                                                  |

Bringing identity in line is a separate, explicit change if it is wanted; nothing in the new work depends on it.

## 16. Reviewing a name

Before adding a name, check: is the term in the [glossary](glossary.md)? Is it English and singular? Does an id column say
which table it points to? Is a boolean really a flag and not a lifecycle? Is a catalogue stored in a lookup table? Is the
legacy name recorded in [`legacy-dictionary.md`](legacy-dictionary.md)? Is the constraint name 63 characters or fewer?
